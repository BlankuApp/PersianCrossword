Brainstorm Report: Local Persian Character Detection in the Grid Importer

Short answer: yes, this is technically feasible, and the current importer is already a strong base for it. The existing pipeline already solves the hardest geometry problem: locating the grid, perspective-correcting it, and dividing it into cells. The next step is to add per-cell character recognition on top of that.

Bottom line
The most practical path is: keep the current grid detection pipeline, crop each open cell after warping, run local OCR or a local single-character classifier on each crop, normalize the result to Persian text rules, and expose low-confidence cells for manual correction in the UI.

1. What the current importer already does well

Today the backend accepts an uploaded image, detects the crossword boundary, warps it into a front-facing rectangle, finds the cell edges, and classifies each cell as either black or open. The response is currently: 

{
  "rows": 15,
  "cols": 15,
  "matrix": [[0,1,0,...], ...],
  "warped_png_b64": "..."
}

That means the importer already produces the exact intermediate artifact needed for OCR: a normalized, perspective-corrected grid with known cell boundaries.

Grid localization already exists Perspective correction already exists Cell boundaries already exist Black/open classification already exists

2. Why per-cell Persian OCR is realistic here

This is not the same problem as doing OCR on an entire noisy newspaper page. Once the grid is warped, the task becomes much smaller: classify one symbol inside one cell. That is a much friendlier problem.

Also, the main app already expects a single Persian grapheme per cell in its state model, and it already normalizes common Arabic/Persian Unicode variants such as ی and ک. That reduces the amount of OCR perfection needed at the raw text level.

Main caveat
Accuracy depends heavily on the image source. Clean screenshots or exported solution images are much easier than low-resolution scans of printed newspaper pages.

3. The core difficulty is not geometry anymore, it is recognition quality

The hard recognition cases will likely be:

  • Very small letters where dots are faint or merged into noise.
  • Letters that differ mainly by dots, such as ب / ت / ث / ن / ی.
  • Confusable groups such as ج / چ / ح / خ and س / ش.
  • Grid lines eating into the glyph near the cell borders.
  • Low-quality scans, compression artifacts, and uneven lighting.
  • Different newspaper fonts or old print styles.

4. Local implementation options

Option Why it fits Main downside Recommendation
Tesseract with Persian language data Fully local, mature, relatively simple baseline, supports Persian language packs. System dependency, often weak on tiny noisy single-cell crops, may confuse similar Persian letters. Best first spike because it is the least invasive baseline.
EasyOCR or similar Arabic-script OCR Fully local, Python-friendly, better modern OCR behavior in many cases. Heavy dependency stack, model download, slower startup, may still be suboptimal for one-cell character classification. Good second baseline if Tesseract underperforms.
Custom single-cell classifier Best match to the actual problem: one symbol inside a bounded cell from a limited alphabet. Needs labeled training data and a training pipeline. Best long-term accuracy path if you have repeated fonts or recurring newspaper sources.

5. The strongest design direction

Because the grid is already segmented into cells, I would treat this as cell classification first, and generic OCR second.

In other words, do not ask an OCR engine to interpret the whole page. Ask it to recognize one pre-cropped symbol in one cell. If the baseline OCR is not accurate enough, the project can evolve toward a dedicated classifier without changing the surrounding importer flow.

6. Proposed pipeline

1. Upload image
2. Detect outer grid
3. Warp grid to a front-facing image
4. Detect cell edges
5. Classify black squares
6. For each open cell:
   - crop inner cell region
   - remove border influence
   - upscale and binarize
   - run local OCR / classifier
   - normalize Persian output
   - attach confidence
7. Return:
   - 0/1 grid
   - per-cell letters
   - per-cell confidence
   - warped image for UI review

7. Preprocessing ideas that will matter a lot

The current importer uses an inner margin to avoid grid lines during black-square detection. The same idea should be reused for OCR crops, but with more care because Persian dots can sit near the top or bottom of the visible glyph.

  • Crop slightly inside the cell border, but not so aggressively that dots get clipped.
  • Upscale each crop 3x to 5x before recognition.
  • Use adaptive thresholding or Otsu thresholding to reduce gray print noise.
  • Optionally remove residual straight border lines using morphology or Hough-line masking.
  • Center the glyph on a clean padded canvas before passing it to OCR.
  • Keep the original grayscale crop too, because some engines work better before hard binarization.

8. Output shape I would consider

The current API only returns the block matrix. For character import, I would not jump straight to exporting grouped answers. I would first return a cell-level result because that is the most debuggable layer. 

{
  "rows": 15,
  "cols": 15,
  "matrix": [[0,1,0,...], ...],
  "letters": [
    ["س", null, "ل", ...],
    ...
  ],
  "confidence": [
    [0.94, null, 0.72, ...],
    ...
  ],
  "warped_png_b64": "..."
}

Once the letters are reliable, grouped answer strings can be derived afterward from the same grid structure. That aligns well with the main app, which stores answers by slot but stores user input by cell.

9. How this connects to the main app model

The main app has two useful target shapes:

  • A block grid, which you already have.
  • One Persian grapheme per white cell, which matches the current crossword state model.

That means the importer can evolve in two stages:

  • Stage A: detect per-cell letters and let the user review them.
  • Stage B: derive across/down answers automatically from those reviewed cells.

10. Practical product direction

Approach What it optimizes for My view
Fully automatic import Speed Possible for clean inputs, but risky without confidence and correction UX.
Semi-automatic import Reliability Best near-term path: OCR suggests letters, user fixes uncertain cells.
Custom trained recognizer High accuracy on your specific sources Best long-term path if you process many similar puzzle images.
Recommendation
Build this as a semi-automatic importer first. Character detection should produce suggestions plus confidence, not pretend to be perfect. That will give you a usable workflow much earlier.

11. Suggested milestone plan

Milestone 1: Cell crop debug mode

Before integrating OCR, expose the cropped image for every open cell and verify that segmentation is correct. If the crops are bad, OCR will not save the pipeline.

Milestone 2: Tesseract baseline

Add a local OCR baseline on top of those crops and measure per-cell accuracy on a small benchmark set. This is mainly to answer one question: is generic OCR already good enough for your data?

Milestone 3: Confidence-driven correction UI

Show the recognized letter inside each cell overlay, color weak predictions differently, and allow quick manual fixes. This will likely deliver a usable tool even if OCR is imperfect.

Milestone 4: Custom classifier if needed

If the generic baseline plateaus too low, switch only the recognition component to a dedicated cell classifier. The rest of the importer can remain the same.

12. Expected accuracy, realistically

I would expect a wide spread depending on input quality:

  • Clean digital puzzle screenshots: likely promising with a generic local baseline.
  • Scanned or compressed newspaper images: likely inconsistent without stronger preprocessing and perhaps a custom model.
  • A single recurring newspaper/font family: strong candidate for a custom classifier with high eventual accuracy.

The key thing to measure is not page-level success. It is per-cell top-1 accuracy after normalization.

13. Questions that would change the design

  • Are the source images clean screenshots, scanner output, or phone photos?
  • Do the puzzles come from one newspaper/font family or many?
  • Is every white cell guaranteed to contain exactly one Persian grapheme?
  • Do you want the importer to return per-cell letters, grouped answers, or both?
  • Is a heavier local dependency acceptable if it improves accuracy?
  • Is first-run model download acceptable, or must everything ship fully offline from the start?

14. Final assessment

Decision
Yes, this is worth pursuing. The current grid importer already provides the right insertion point for local Persian character detection. The safest path is to add OCR after cell segmentation, return per-cell letters with confidence, and design the UI around quick correction. If your inputs are clean, a generic OCR baseline may be enough. If not, this problem is an excellent candidate for a custom single-cell Persian classifier.
